# Semiotic Class Extension

Use this when adding or improving one semiotic class for a language that already exists.

## 1. Inspect Existing Shape

Read:

- `nemo_text_processing/text_normalization/<lang>/taggers/<class>.py`
- `nemo_text_processing/text_normalization/<lang>/verbalizers/<class>.py`
- `nemo_text_processing/inverse_text_normalization/<lang>/taggers/<class>.py`
- `nemo_text_processing/inverse_text_normalization/<lang>/verbalizers/<class>.py`
- Composer files: `taggers/tokenize_and_classify.py`, `verbalizers/verbalize.py`
- Existing tests and test case files for the class

Only read the direction that applies.

## 2. Choose Comparable Implementations

Compare at least one rich implementation and one nearby language when possible.

Examples:

- `en`: broadest class coverage and base conventions.
- `es`, `fr`, `de`: gender, locale, inflection, measurement/date patterns.
- `pt`, `vi`, `ko`: newer language implementations with many classes.
- `rw`, `hy`, `mr`: smaller language/class scaffolds.

Use comparable code to learn patterns, not to blindly copy.

## 3. Define The Class Contract

Write examples before coding:

```text
Input:
Token:
Output:
Should not normalize:
Requires context:
```

For both TN and ITN, when applicable:

```text
TN input: 12 kg
TN token: measure { cardinal { integer: "twelve" } units: "kilograms" }
TN output: twelve kilograms

ITN input: twelve kilograms
ITN token: measure { cardinal { integer: "12" } units: "kg" }
ITN output: 12 kg
```

If the class needs nested tokens, decide whether the verbalizer must support field permutation or `preserve_order: true`.

Before adding broad patterns, read `class-ownership-and-boundaries.md` and write down why this class owns the input. Be especially cautious with bare numbers, abbreviations, names, and short codes that could belong to `cardinal` or `word`.

## 4. Update Data First

Add or revise TSV files for closed inventories:

- digits and zero
- months and days
- currencies
- measurement units
- designators and abbreviations
- whitelist entries

Prefer reusing existing language TSVs over creating class-specific duplicates. If reuse produces one wrong contextual form, add a local rewrite instead of duplicating the whole table.

## 5. Implement The Tagger

The tagger should:

- Restrict the input domain enough to avoid capturing ordinary words.
- Emit a stable token schema with `add_tokens()`.
- Expose reusable subgraphs when higher-level classes depend on it.
- Use weights to resolve class conflicts intentionally.

Avoid broad `NEMO_SIGMA` matches unless they are tightly bounded.

## 6. Implement The Verbalizer

The verbalizer should:

- Delete the token wrapper with `delete_tokens()`.
- Accept the token field orders generated by `TokenParser`, or require `preserve_order: true` in the tagger.
- Keep punctuation and spacing behavior explicit.
- Preserve nested class behavior by reusing lower-level verbalizers when possible.

## 7. Wire The Class

Check:

- Import and instantiate tagger in `taggers/tokenize_and_classify.py`.
- Include the class graph in the weighted `classify` union.
- Import and instantiate verbalizer in `verbalizers/verbalize.py`.
- Include the class graph in the verbalizer union.
- Add final/post-processing integration only if the language already uses it or the behavior requires it.

## 8. Add Tests

Add class-specific tests if they do not exist:

```text
tests/nemo_text_processing/<lang>/test_<class>.py
tests/nemo_text_processing/<lang>/data_text_normalization/test_cases_<class>.txt
tests/nemo_text_processing/<lang>/data_inverse_text_normalization/test_cases_<class>.txt
```

Cover:

- base examples
- zero and one
- plural/singular or gender/case variants
- punctuation adjacency
- ambiguous inputs that should remain words
- cased input when supported
- nested class examples such as measure + decimal

## 9. Review Packet

Summarize:

- Token schema.
- Linguistic rules encoded.
- Similar language patterns reused.
- Tests added.
- Known unsupported cases.
